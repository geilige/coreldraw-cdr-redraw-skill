# 位图 → 矢量 → CDR 实战笔记

这份文档记录把栅格参考图（PNG/JPG）还原成可编辑 CDR 时踩过的坑与验证过的做法。
全部结论来自 CorelDRAW X8 + pywin32 + potracer 的实测。

---

## 1. 总体流水线

```
参考图 ──┬─► 标定（mm/px）───► 分区 ──► 灰度上采样 ──► 二值化 ──► 描摹 ──► SVG
         │                                                              │
         └──────────────────────────────────────────────────────────────┤
                                                                        ▼
                            CorelDRAW：建页 → 建图层 → 导入 SVG 定位 → 保存 → 导出预览
                                                                        │
                                                                        ▼
                                        配准比对：渲染图贴回页面 ──► IoU / 召回 / 精确
```

对应脚本：

| 步骤 | 脚本 |
| --- | --- |
| 标定 + 分区 + 描摹 + 参数寻优 | `scripts/cdr_image_trace.py` |
| 建页 + 建图层 + 导入定位 + 保存导出 | `scripts/cdr_image_place.py` |
| 配准式像素校验 | `scripts/cdr_visual_diff.py` |

## 2. 标定：先把 mm/px 定下来

参考图没有物理尺寸时，用**用户给出的权威尺寸**标定，通常是页面宽度：

```
mm_per_px = page_width_mm / image_width_px
```

**务必检查图宽高比是否等于给定页面宽高比。** 例如：

- 源图 1217 × 1660 → 比例 0.7331
- A4 210 × 297 → 比例 0.7071

两者不等，说明源图不是标准 A4 比例（裁切过，或含边距）。此时按宽度标定，
纵向内容高度 = `1660 × 0.172555 = 286.442 mm`，与 297 mm 的页面高度差 10.6 mm。
这个差值**必须在报告里说明**，不要静默拉满，否则整版纵向比例都会错。

### 扫描/裁切残留必须探测

源图边缘常带非设计内容。实测案例：源图最左侧 4 列（x=0..3）是纯黑
（列均值 15，而第 4 列起为 231），贯穿全高——这是裁切残留，不是设计元素。

探测方法：逐边取首/末行或列求均值，低于阈值即判为暗边；再统计左侧连续暗列数。
`cdr_image_trace.py` 的 `probe_edges()` 会给出 `left_dark_cols`，
配合 `--crop-left N` 排除。

**判断原则**：全高/全宽的等宽暗条、边缘灰线、色偏条，几乎都是残留，不要复刻；
但要在交付说明里提一句，避免用户以为漏画。

## 3. 分区：内容块要分开描摹

整页一次性描摹会让不同性质的区块互相干扰（色带、线稿、反白字、小字）。
按内容性质分区，每区单独设参数：

| 区块类型 | invert | 典型参数 |
| --- | --- | --- |
| 满版色块 | 不描摹，用原生矩形 | — |
| 精细线稿插图 | False | U=8, ts=3, **am=1.0**, ot=0.1 |
| 深底上的反白字标 | **True** | U=8, ts=2, **am=1.0**, ot=0.1 |
| 小字号文字（6pt 级） | False | U=8, ts=2, **am=1.0**, thr≈118 |

> `alphamax` 一律用 1.0。早先笔记里写"图标类用 0.0~0.5"是**错的**，
> 那是被"alphamax=0 的 IoU 反而最高"误导的结论，详见 §5.4。

`cdr_bitmap_to_cdr.py` 会自动分区。三条判据都有坑，逐条记：

### 3.1 贯穿边缘的扫描残留必须先剥离

残留条（裁切黑边、扫描黑边）会让**每一行**都含有墨迹像素，行投影就永远
找不到空隙，分区会把本应分开的区块粘成一整块。

实测 vonder 图：左侧 4px 贯穿全高的黑边条，把易碎标（y 338..447）、
插图（y 500..900）、页脚（y 1075..1106）粘成了一个 `y 0..901` 的大块。

做法：抹掉"整列/整行几乎全暗"（占比 > 0.9）的边条后再投影。
注意抹除**只用于分区判定**，不要缩小色带的横向范围（见 3.3）。

### 3.2 判定"满版色带"要用行的中位数，不要用覆盖率

色带中间常被反白字标掏空，覆盖率会掉到 0.85 以下，用覆盖率判定会把整条
色带误判成普通内容区。实测同一张图：

| 判定信号 | 结果 |
| --- | --- |
| 行覆盖率 ≥ 0.85 | 碎成 `901..960` + `1037..1059` 两段（**错**） |
| **行中位数 < 128** | **`901..1059` 整条**（对） |
| 行 25 分位 < 128 | 多出 `661..784` 假色带（插图密集区，**错**） |

行中位数只看"这一行整体是深还是浅"，不受中间被掏空影响。
25 分位太靠下沿，插图密集区也会低于 128，会误判。

色带要拆成两件事：垫底的原生矢量**矩形**（颜色取源图暗像素 RGB 中位数，
实测 vonder 得 `#121011`）+ 同一框内的**反白描摹**（invert=True）。

### 3.3 色带的横向范围用未剥离残留的墨迹

满版底色本来就该顶到页边。残留剥离只用于"哪里是内容"的判定，
不该把色带缩进去（否则色带左边会少 0.69mm）。

### 3.4 区域外沿要用**宽松**墨迹图向外扩，不要用严格图收紧

细笔画的末梢（文字 descender、抗锯齿边缘）每行只有两三个墨迹像素，
会被 `min_ink_px` 当成空白切掉。

实测 vonder 页脚：墨迹真实范围 y 1083..**1098**，严格图（gray<128）只到 1096，
切掉下缘后召回从 96.69% 掉到 86.65%，IoU 从 93.6% 掉到 84.7%。

做法：用宽松图（gray<200，含抗锯齿过渡像素）逐行/逐列向外扩，
**遇到真正的空白行/列就停**。不要改成无脑 padding——padding 会越过区块间
空白伸进相邻区域，把邻块墨迹也描一遍，在 CDR 里产生重复几何。

### 3.5 自动分区够用吗

够。实测 vonder 图自动分区与手工调优的毫米包围盒一致到 0.1mm：

| 区域 | 自动分区（mm） | 手工调优（mm） |
| --- | --- | --- |
| 色带 | 0.000,155.472..210.000,182.736 | 0,155.472..210,182.736 |
| 插图 | 56.253,96.631..170.312,152.539 | 56.253,96.545..170.291,152.604 |
| 易碎标 | 152.539,59.532..194.988,75.924 | 152.474,59.596..195.074,75.924 |
| 页脚 | 81.274,186.878..145.292,189.121 | 81.252,186.921..145.249,189.703 |

自动分区给出的名称（`art01` / `mark01` / `text01`）只是**命名启发式**，
按尺寸猜的，不代表真实语义；需要更贴切的名字就手工给 `--region`。

## 4. potracer 的三个致命细节

### 4.1 构造器内部会 invert()

`potrace.Bitmap(arr)` 内部执行了一次 `invert()`，它约定的输入是
**True = 白色**。所以要描摹黑色前景时，必须传 `~fg`：

```python
path = potrace.Bitmap(~fg).trace(...)   # fg 中 True = 要描摹的墨迹
```

传错的症状：整图反相——该黑的地方白、该白的地方黑，或描出巨大背景轮廓。

### 4.2 没有 curves_tree，必须用 evenodd

potracer 只实现顶层 `path.curves`，不提供父子包含关系，因此镂空（字母 O 的内孔、
圆环）无法靠 nonzero 规则还原。SVG 必须写：

```xml
<path fill="#111111" fill-rule="evenodd" d="..."/>
```

even-odd 规则下，奇数次覆盖为填充区，天然还原镂空。

### 4.3 子路径分隔符必须带空格

`"Z" + "M..."` 拼成 `"...ZM..."` 是**合法 SVG**，浏览器和 Inkscape 都能正确渲染。
但 **CorelDRAW X8 的 SVG 解析器会误解**，产生桥接三角形伪影（相邻子路径被连线）。

必须用空格分隔：

```python
d=" ".join(subpaths)      # 得到 "...Z M..."
```

最小复现验证：同一个 evenodd 路径，`ZM` 连接时 X8 出伪影，`Z M` 连接时正常。

## 5. 参数：小图形必须上采样后再描摹

### 5.1 症状

8 mm 宽的图标（酒杯、箭头）在原分辨率直接二值化描摹会明显变形：

- 平顶杯口被圆滑成尖拱
- 细直杯脚被简化为歪斜折线，粗细不均
- 底座变成波浪块

### 5.2 真正的解法是上采样，不是 alphamax

原图上细笔画只有 1–2 px，二值化后是锯齿状 1px 折线，potrace 只能拟合出扭曲曲线。

**解法：对灰度做 LANCZOS 上采样再二值化。** 抗锯齿灰阶被放大成
平滑梯度，二值化边界更接近真实轮廓。

实测（酒杯图标，与源掩膜比 IoU + 形状是否正确）：

| 方案 | IoU | 形状 |
| --- | --- | --- |
| U=1，alphamax=1.0 | 72.47% | **失真**（尖拱杯口 + 弯折杯脚） |
| U=1，alphamax=0.0 | 71.17% | **失真**（同上） |
| U=4，alphamax=1.0 | 81.37% | 正确，曲线平滑 |
| U=4，alphamax=0.5 | 81.66% | 正确，曲线平滑 |
| U=4，alphamax=0.0 | 81.82% | 形状正确但**是纯多边形** |

结论：**U=1 时怎么调 alphamax 都救不回来；U≥4 时 alphamax 取 0.5~1.0 都很好。**
上采样才是关键，alphamax 只决定曲线平滑度。

### 5.2.1 上采样倍数：4 是及格线，8 更好

以「源图原生分辨率的抗锯齿渲染 IoU」为指标（见 5.7），实测：

| 区域 | U=4 | U=8 | 提升 |
| --- | --- | --- | --- |
| vonder 字标 | 99.38% | **99.51%** | +0.13 |
| Fragile 标 | 95.23% | **98.25%** | +3.02 |
| 工具群插图 | 96.53% | **97.55%** | +1.02 |
| 6pt 页脚文字 | 88.20% | **93.81%** | +5.61 |

U=8 全面更好，小尺寸内容收益最大。代价是子路径数增加、文件变大、描摹变慢
（大区域 U=8 单次描摹可达 80 秒）。**建议默认 U=8**；
超大区域（整版插图）可用 4 控制耗时，或用 `--probe` 实测决定。
U=12 收益递减，一般不必。

同时注意：U 越大，`alphamax` 越应该取 1.0——像素足够多时
最大平滑才是安全的，不会把拐角磨圆成失真。

### 5.3 turdsize 必须随 U² 折算

`turdsize` 是"丢弃面积小于该值的斑点"，单位是**位图像素**。
上采样 U 倍后面积变为 U² 倍，所以：

```python
turdsize_internal = turdsize_source_px * U * U
```

忘记折算会把本该保留的细节当斑点删掉。

### 5.3.1 二值化阈值直接决定笔画粗细

`fg = (gray < threshold)`。阈值越低，算作墨迹的像素越少，**笔画越细**；
阈值越高笔画越粗。

默认 128 对大多数内容都合适（抗锯齿的 50% 覆盖点）。但**细笔画文字**
（6pt 级、笔画只有 1–2 px）对阈值非常敏感，值得扫一遍：

实测（源图原生分辨率 IoU）：

| 描摹阈值 | 页脚 IoU | 页脚面积比 |
| --- | --- | --- |
| 110 | 87.33% | 0.912 |
| 118 | **93.81%** | 0.998 |
| 128 | 88.20% | 0.998 |
| 140 | 86.91% | 1.074 |
| 155 | 83.79% | 1.156 |

注意 IoU 在 118 附近有明显峰值——**阈值不是"越接近 128 越好"，要实测**。
面积比则随阈值单调变化，是判断粗细的可靠依据。

### 5.4 ⚠️ alphamax=0 是个陷阱

potrace 文档：`alphamax` 是拐角阈值，"If this parameter is 0, then no smoothing
will be performed and the output is a **polygon**"。

实测：`alphamax=0.0` 时输出 SVG 里**曲线段 C 的数量为 0**，全部是直线段 L，
圆角被切成折线（chamfer）。

危险之处在于：**它的像素 IoU 反而最高**（因为折线更贴合二值边界），
如果只看 IoU 选参数，会选出视觉上最差的多边形结果。

**判断方法**：不要只看 IoU，还要数 SVG 里的 `C` 与 `L` 数量：

```python
nc, nl = svg.count("C"), svg.count("L")   # 曲线段 / 直线段
```

曲线段为 0 说明退化成了多边形，必须提高 alphamax。

### 5.5 参数语义速查

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `alphamax` | 拐角阈值；**0 = 纯多边形，1.0 = 最大平滑** | 图标/文字用 **0.5–1.0**；不要用 0 |
| `opttolerance` | 曲线合并容差 | 越大越简并；精细内容用 0.1 |
| `opticurve` | 是否做曲线优化 | 1 |
| `turdsize` | 斑点面积阈值 | 见 5.3 |
| `upscale` | 描摹前灰度上采样倍数 | **8（对细部保真最关键）** |

### 5.6 本地评估，不要反复走 CorelDRAW

改参数后不必每次都导入 CDR 导出比对——那样一轮要十几秒。
写一个**极简 SVG 光栅化器**即可本地打分：

1. 解析 path 的 `M/L/C/Z`，三次贝塞尔离散成折线；
2. **even-odd 填充 == 各子路径覆盖区异或**，所以逐子路径 `cv2.fillPoly` 后
   全部 XOR 起来就是最终掩膜；
3. 把结果光栅化回**源像素网格**，与该区域二值掩膜算 IoU / 召回 / 精确。

`cdr_bitmap_to_cdr.py` 的逐区寻优与 `cdr_image_trace.py --probe` 就是这套逻辑。

#### ⚠️ 光栅化必须超采样，否则寻优会选错阈值

**这是本流程最隐蔽的一个偏差。** `cv2.fillPoly` 是"取整后填充"的**硬边**
光栅化，会系统性低估矢量覆盖面积（sub-pixel 偏差）。在源图原生网格上
（约 5.8 px/mm）这个偏差不可忽略，而且方向固定：**笔画越粗，硬边 IoU 越高**。
于是寻优会一路爬到最粗的阈值。

实测同一区域（band 反白字标，U=8）：

| 阈值 | 硬边 IoU% | 超采样 IoU% | 超采样面积比 |
| --- | --- | --- | --- |
| 112 | 93.72 | 98.70 | 1.013 |
| 128 | 94.15 | 99.40 | 1.005 |
| **138** | 94.29 | **99.51** | **1.000** |
| 148 | **94.34（硬边最高）** | 99.35 | 0.996 |

硬边把最优判成 148（过粗），超采样判成 138（正确）；
而 CorelDRAW 实际导出比对是 99.15%，说明超采样才贴近真实。

**做法**：先按 `ss` 倍超采样（`ss=8`），再盒式降采样得到覆盖率 0..1，
以 `覆盖率 >= 0.5` 作为墨迹判据。

**顺带必须做包围盒局部化**：不要为每个子路径分配整幅画布。一个 483 子路径的
区域在 ss=8 下整幅分配要做 483 × (5288 × 2592) ≈ 66 亿次像素操作，根本跑不完。
改为按子路径自身的包围盒分配小画布、再 XOR 回总画布，代价降几个数量级。

> 注意：偏差是 sub-pixel 效应，在**远高于源图密度**的网格上可以忽略。
> 比如按 60 px/mm 数矢量面积算面积比（见 5.7）用硬边没问题，
> 但在源图原生网格上算 IoU 就必须超采样。

**注意评估渲染倍率**：如果按 1× 源分辨率渲染，曲线会被像素化掩盖，
看不出"圆角被切成折线"这类问题。要判断曲线质量，需**按 4–8× 渲染**再观察，
或直接数 SVG 里 `C` / `L` 的数量（见 5.4）。

### 5.7 判断笔画粗细：用「面积比」，不要靠眼睛

**最容易踩的坑**：把源图和重绘导出图放在同一张对照图里并排看，
就断言"重绘笔画偏粗"。这往往是**对照图本身有缺陷**造成的错觉。

原因：源图原生密度（例如 1217px 宽 → 5.795 px/mm）与 CorelDRAW 导出密度
（例如 2480px 宽 → 11.81 px/mm）不同。两张图裁同一毫米范围后，
导出图的像素数多一倍，放大同样倍数后**显示尺寸不同**，重绘自然显得又大又粗。

更隐蔽的是：**任何高于源图原生密度的比对都会让重绘显得偏粗**——
因为源图必须被上采样，模糊后细笔画在固定阈值下会缩水。

#### 可靠做法：算墨迹面积（mm²），与分辨率无关

```python
# 源图墨迹面积
area_src = source_ink_pixels * (mm_per_px ** 2)

# 矢量几何面积：按 60 px/mm 硬边光栅化后数像素，量化误差可忽略
area_vec = vector_pixels_at_60ppm / (60.0 ** 2)

# 比值越接近 1.000，笔画粗细越吻合
ratio = area_vec / area_src
```

**换算陷阱**：`ox = vx - x0 * S` 里的 `x0` 若是**源图像素坐标**才要乘 `S`；
若 `x0` 已经是从 SVG viewBox 读出的**毫米**值，就直接 `vx - x0`，
再乘一次 `S` 会让坐标跑到画面外、光栅化结果全为 0。

实测（某次真实交付的最终结果）：

| 区域 | 源图面积 mm² | 矢量面积 mm² | 面积比 |
| --- | --- | --- | --- |
| 工具群插图 | 2344.34 | 2384.64 | 1.017 |
| vonder 字标 | 656.31 | 654.46 | 0.997 |
| Fragile 标 | 373.59 | 373.00 | 0.998 |
| 6pt 页脚文字 | 50.41 | 50.85 | 1.009 |

**全部落在 0.997–1.017**，即笔画粗细偏差 ≤ 1.7%。
此时若对照图里仍显得"重绘更粗"，那是对照图的尺度问题，不是几何问题。

#### 不要这样测

```python
# ❌ 把导出图 LANCZOS 降采样到源图尺寸后阈值化——
#    会给细笔画补边，实测把 1.00 的面积比放大成 1.39
b = export_img.resize(source_img.size, Image.LANCZOS)
```

### 5.8 对照图必须同尺度

给用户看的源图/重绘对照图，必须先把两者重采样到**同一 px/mm** 再并排：

```python
PPM = 24.0                       # 统一的毫米像素密度
a = src.crop(src_box).resize((w_mm * PPM, h_mm * PPM), Image.LANCZOS)
b = export.crop(exp_box).resize((w_mm * PPM, h_mm * PPM), Image.LANCZOS)
# 再并排 + 同尺度差异图
```

否则面板尺寸不一致，用户会以为重绘变形了。
另外差异图要标清楚图例（深灰=一致 / 红=仅源图 / 蓝=仅重绘），
避免把 1px 级的抗锯齿边缘当成错误。

## 6. CorelDRAW X8 COM 的实测坑

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `GetActiveObject` 抛 `com_error(-2147221021, '操作无法使用')` | MK_E_UNAVAILABLE，X8 未注册到 ROT | 改用 `Dispatch("CorelDRAW.Application.18")`，会复用已开实例 |
| `TypeError: The Python instance can not be converted to a COM object` | 签名含**可选 VT_DISPATCH 参数** | 末尾显式补 `None`：`doc.SaveAs(p, None)`、`lay.Import(p, 0, None)`、`doc.Export(p, 802, 1, None, None)` |
| `ExportEx` 返回成功但不写文件 | X8 已知缺陷 | 以 `Export` 为主，且必须用 `os.path.exists` + 文件大小确认 |
| `page.Shapes.All.Count` → `AttributeError` | `All` 是方法 | 写 `page.Shapes.All().Count` |
| 导入后拿不到形状对象 | `Layer.Import` 无返回值 | 见下条 |
| **两个形状的属性互换了** | **`Layer.Import` 把新形状插到图层"底部"（索引 1），不是追加到末尾**；图层里已有形状时 `Item(Count)` 取到旧形状 | 用"导入前后名称集合的差"定位新形状；或一个区域一个图层，让导入时图层为空 |
| 画面不刷新 / 文件没落盘 | Optimization 未复位 | 结束后 `Optimization=False; EventsEnabled=True; app.Refresh()` |
| `app.ActiveDocument = doc` → `AttributeError` | 该属性**只读** | 用 `doc.Activate()` 切换活动文档 |
| 保存后文件不在预期位置 | `SaveAs`/`Export` 按 CorelDRAW 自己的工作目录解析**相对路径** | 调用前把路径 `os.path.abspath()` |
| 重新打开 CDR 后坐标值大了一截 | `Document.Unit` **不随文件保存**，重开回到英寸 | 读坐标前先 `doc.Unit = 3`（几何本身是绝对单位，未受影响） |

### 常量速查（X8 实测值）

| 名称 | 值 |
| --- | --- |
| `cdrMillimeter` | **3**（不是 4） |
| `cdrPortrait` | 0 |
| `cdrTopLeft` | 3 |
| 导出滤镜 `cdrPNG` | 802 |
| 颜色模式 `cdrRGB` | 4 |

### 坐标转换

CorelDRAW 的 y 轴向上，设计稿习惯以左上为原点：

```python
doc.ReferencePoint = 3            # cdrTopLeft
shape.SetPosition(x_mm, page_height_mm - y_top_mm)
```

### ⚠️ Layer.Import 是插到图层底部，不是追加到末尾

这是本项目踩过的最贵的一个坑，因为它**只在特定图层结构下才暴露**，
一旦手工配置换成自动配置就会突然发作。

X8 的 `Layer.Import` 把新形状插到图层形状列表的**索引 1（z 序最底）**，
而不是追加到末尾。所以下面这行只在"导入前图层是空的"时才正确：

```python
lay.Import(svg, 0, None)
sh = lay.Shapes.Item(lay.Shapes.Count)      # ← 图层非空时会取到旧形状
```

实测症状：垫底矩形和反白字标被放进同一个 `BAND` 图层后，
`Item(Count)` 取到了矩形，于是把**字标的尺寸/位置/填充**写到了矩形上，
而字标保留了导入时的原始几何。结果：

| 形状 | 应该是 | 实际变成 |
| --- | --- | --- |
| `band01`（矩形） | 210 × 27.264 mm，深色 `#121011` | 70.856 × 19.801 mm，白色 |
| `band01_ink`（字标） | 70.856 × 19.801 mm，白色 | 70.852 × 19.775 mm，深色 `#111111` |

导出图里表现为：**整条色带消失、字标变成黑字压在插图上**。
而定位日志仍打印"误差 0.000mm [OK]"——因为日志打印的是**请求值**，
没有核对实际值，错误被完全掩盖。

两个修法，建议同时做：

1. **一个区域一个图层**，让导入时图层为空，索引无歧义。
2. 定位新形状用"导入前后名称集合的差"，对插入位置不敏感：

```python
before = {str(lay.Shapes.Item(i).Name) for i in range(1, lay.Shapes.Count + 1)}
lay.Import(svg, 0, None)
after = {i: str(lay.Shapes.Item(i).Name) for i in range(1, lay.Shapes.Count + 1)}
added = [i for i, nm in after.items() if nm not in before]
sh = lay.Shapes.Item(added[0]) if len(added) == 1 else lay.Shapes.Item(lay.Shapes.Count)
```

**并且矩形也要核对实际值**：`CreateRectangle2` 的参数语义在各版本间有差异，
只打印请求值而不读回 `PositionX / SizeWidth` 会掩盖错误。

> 教训推广：凡是"创建/导入后立刻按索引取回"的写法都要警惕。
> 宁可多读一次属性核对，也不要假设插入位置。

## 7. 校验：必须配准后再比

### 7.1 陷阱

CorelDRAW 导出的位图通常是**内容包围盒**，不是整页。
实测：A4 页面上内容区为 210 × 130.065 mm，导出 PNG 就是 2480 × 1536，
比例 1.6146——直接和 210 × 297 的整页源图比，IoU 只有 11.82%，完全无意义。

### 7.2 正确做法

1. 从 `placement.json` 读内容包围盒 `content_bbox_mm`；
2. 建一张整页白底（如 2480 × 3507）；
3. 把渲染图**按包围盒高度归一并贴到 `y = bbox_top * px_per_mm`**；
4. 源图也贴到同一张整页白底；
5. 再逐像素算 IoU / 召回 / 精确，并输出差异叠加图。

### 7.3 指标怎么读

- **IoU**：整体重合度，主体配准后通常在 85%–95%。
  达不到 100% 是正常的——描摹必然在边缘产生 1px 级偏差。
- **召回**（源被覆盖比例）：低说明**漏画**，通常是小字/细线丢失。
- **精确**（绘制正确比例）：低说明**多画/变粗**，通常是描摹把细笔画加粗。

实测参考（一次真实交付：210×297mm 包装封面，源图 1217×1660）：

**整页配准**（渲染图按内容包围盒贴回整页，2480px 比对）：

| 指标 | 数值 |
| --- | --- |
| IoU | 93.48% |
| 召回 | 95.33% |
| 精确 | 97.97% |

**分区域**（源图原生分辨率，更严格）：

| 区域 | IoU | 召回 | 精确 | 面积比 |
| --- | --- | --- | --- | --- |
| vonder 反白字标 | 99.51% | 99.88% | 99.35% | 0.999 |
| Fragile 标 | 98.25% | 99.62% | 98.63% | 1.010 |
| 工具群插图 | 97.55% | 99.48% | 98.05% | 1.015 |
| 6pt 页脚文字 | 93.81% | 96.69% | 96.92% | 0.998 |

结论：反白大字号 ≈ 99.5%，精细插图 ≈ 97.5%，
**小字号文字仍是天然短板（≈ 94%）**，但已远好于初版方案的 88%。

### 上采样带来的实际提升

同一交付，把描摹前改为「灰度 LANCZOS 上采样 8× 再二值化」并按原生分辨率
IoU 重选参数（阈值也一并扫）后：

| 区域 | 改前 IoU | 改后 IoU | 提升 |
| --- | --- | --- | --- |
| vonder 字标 | 94.90% | 99.51% | +4.61 |
| Fragile 标 | 86.67% | 98.25% | **+11.58** |
| 工具群插图 | 81.74% | 97.55% | **+15.81** |
| 6pt 页脚文字 | 60.29% | 93.81% | **+33.52** |

笔画面积比从 0.997~1.017 进一步收敛到 **0.993~1.007**。

Fragile 标提升最大的原因是酒杯图标由明显失真恢复为完全正确
（尖拱杯口 → 平口杯身）。这印证了 5.2 的结论：**上采样是保真的关键**。

### 7.4 小字号文字怎么办

6pt 级文字在原图上只有十几像素高，描摹必然失真（笔画粘连、粗细不均）。
两条路：

1. **保留描摹**：视觉可读即可，需在交付说明里注明"文字为描摹轮廓，非活字"。
2. **改活字**：确认字体后用 CorelDRAW 文本对象重建，可编辑、印刷更锐利，
   但需要用户确认字体，否则字形对不上反而更糟。

不要默认选 2——字体猜错比描摹失真更严重。

- [ ] mm/px 标定依据已记录（用户给的尺寸 or 页面尺寸）
- [ ] 图比例与页面比例不一致时已说明纵向差异
- [ ] 源图边缘残留（暗边/灰线）已探测，且未复刻，并已在报告中提及
- [ ] 每个区域的描摹参数与 IoU 已记录
- [ ] CDR 里每个元素的**目标坐标 / 尺寸 vs 实际**误差 < 0.02 mm
- [ ] 图层齐全、命名清晰、z 序正确
- [ ] CDR 已保存且文件大小合理（非 0，非异常小）
- [ ] 预览图导出成功（用文件存在性确认，不只看有无异常）
- [ ] 整页配准 IoU / 召回 / 精确已算出，并附差异叠加图
- [ ] 报告里的还原度数字与 `compare/metrics.json` **一致**
      （不一致说明报告是在校验之前写的，见下节）
- [ ] 反白元素（深底白字）填充为白色，不是黑色描边
- [ ] 明确告知用户：CDR 文件路径、内容构成、已知偏差与来源

### 8.1 报告的写入顺序：必须在校验之后

报告里的数字来自两个阶段（步骤 4 逐区寻优在前、附加配准校验在后）。
把写报告排在校验**之前**，报告里的还原度就会停留在空值/旧值——
实测症状是 `report.md` 写 `整页 IoU 24.47% / 召回 37.31%`，
而 `compare/metrics.json` 里是 `93.62% / 95.14%`。交付物里两个文件互相矛盾，
比数字偏低本身更糟。

修法有两层：

1. **顺序**：`write_report()` 放在 `validate()` 返回之后。
2. **可重建**：把报告所需的一切写进 `svg/manifest.json`——
   每区的 `iou/recall/precision/ink_ratio`、垫底矩形 `rects`、
   图层顺序 `layer_order`、`page_h_explicit`。
   这样 `--report-only` 能几秒钟重建报告，不必重跑十几分钟描摹
   （U=8 下一次大区域描摹要几十秒，五档阈值扫描整轮要十几分钟）。

读清单时缺字段要显示 `—` 而不是 0：0 会被误读成"完全不像"，
而真实含义是"这一版清单还没记录"。同理，若清单没有 `rects`（旧版），
满版色带的垫底矩形可由该区域的 `bbox_mm` 反推，报告不至于缺段。
